## Описание проекта
В этом проекте реализована инфраструктура контейнерезации(Docker) и системы непрерывной интеграции и доставки(CI/CD GitHub Actions) для разработки многокомпонентной web-системы на примере интернет магазина написанного с помощью библиотеки React(часть Frontend) и фреймворка Django(часть Backend).

## Цели и задачи проекта
### Основная цель проекта:
Проектирование и реализация отказоустойчивой, автоматизированной инфраструктуры для разработки и развертывания web-приложения с использованием современных DevOps-инструментов, исключающих ручное вмешательство при обновлении системы.
### Проблемы решаемые данным проектом:
* **Освобождает от рутинных процессов, ускоряя время разработки и позволяя разработчикам сосредоточится на бизнес логике проекта:** Разработчику больше не нужно отвлекаться от написания кода на React или Django, чтобы вспомнить команды SSH, настроить веб-сервер или вручную копировать файлы сборки. Он просто создаёт Pull Request для продакшен разработки, а в случае локальной разработки прописывает команду `docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d --build` для запуска и автоматического пересбора контейнеров при изменении конфигурации или установке новых библиотек, а в случае изменений в коде проекта они подхватываются на «на лету» прямо внутри контейнеров благодаря hot-reload (встроенный в React и Django),  сохраняя высокую скорость локальной разработки.
* **Повышает качество и надежность создаваемого приложения:** Благодаря этапу CI(Continuous Integration) в GitHub Actions, автоматические тесты (как для Django, так и для React) и линтеры (проверка стиля кода, например, Flake8, ESLint) запускаются при каждом изменении кода до попадания в продакшен и в случае ошибок на данном этапе программа просто не попадет на боевой(тестовый) сервер. А благодаря контейнерезации мы добивемся «Качество через стандартизацию». Docker гарантирует, что код исполняется в абсолютно одинаковой среде на компьютере разработчика, на этапе тестирования в GitHub Actions и на боевом сервере (Production). Исчезает целый класс плавающих багов, связанных с разницей версий операционных систем, библиотек или Python/Node.js. Если код стабильно работает в контейнере локально, он точно так же запустится и на сервере.
* **Делает разработку удобной для командной разработки:** В команде у каждого из разработчиков могут разные компьютеры, работающие на разных операционных системах: кто-то работает на Windows, кто-то на macOS, кто-то на Linux. Без Docker у каждого разработчика были бы свои настройки проекта(библиотки, файлы конфигурации и т. д.). Docker изолирует зависимости внутри контейнера. Новый разработчик скачивает репозиторий, пишет одну команду в терминале и через 2 минуты имеет точно такую же рабочую копию проекта, как и вся команда. А благодоря CI/CD GitHub Actions когда несколько человек одновременно пишут код при создании Pull Request (запроса на слияние кода) автоматически проверяется, не ломает ли код одного разработчика тесты, написанные другим разработчиком. Слияние блокируется, пока код не станет идеальным.

### Задачи проекта:
* **Разработка тестового макета приложения:** Создание небольшого Full-stack веб-приложения интернет-магазина на стеке **Django**(часть Backend) и **React**(часть Frontend) для тестирования инфраструктуры.
* **Контейнерезация с помощью Docker:** Разработка файлов `Dockerfile` для фронтенда и бэкэнда c использованием многоэтапной сборки(*multi-stage builds*) для минимизации веса итоговых образов. 
* **Разделение окружений и оркестрация контейнеров:** Разработка гибкой системы оркестрации на базе трех файлов `docker-compose` для разделения сред разработки и продакшена.
* **Маршрутизация трафика(Nginx):** Конфигурация веб-сервера Nginx для маршрутизации, проксирования API-запросов и отдачи статики. 
* **Автоматизация процессов(CI/CD):** Создание автоматизированного пайплайна для контроля качества кода и автоматического  деплоя по триггеру из Git.
* **Управление конфигурацией и безопасность:** Вынос конфигурационных и конфеденциальных данных в файл `.env` c добавлением его в 
`.gitignore` для предотвращение попадания в публичный Git-репозиторий. В место него в публичный репозиторий попадет файл - макет 
`.env.example` с перечнем всех необходимых переменных с дефолтными значениями. Его можно использовать для разработки, скопировав его содержимое в файл `.env`, заполнив его актуальными данными. Для автоматического деплоя на продакшен-сервере содержимое финального файла `.env` должно быть занесено в **GitHub Secrets** репозитория под именем `ENV_FILE`. Во время работы пайплайна GitHub Actions автоматически извлекает секрет, создает рабочий `.env` файл на сервере, исключая утечку данных.
